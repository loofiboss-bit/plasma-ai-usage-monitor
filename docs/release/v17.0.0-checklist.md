### Phase 3 — Runway engine

- [x] Add pure `RunwayQuery` quota and budget calculations plus read-only,
  short-lived SQLite data access. No SQL or forecast calculation runs in QML.
- [x] Implement quota runway with four compatible samples, a 15-minute minimum
  span, a 15-minute freshness limit, one stable reset/window/source/unit/limit,
  numeric-zero preservation, non-monotonic/reset rejection, sparse-gap
  coverage, and a deterministic bounded Theil-Sen slope over at most 256
  evenly selected samples.
- [x] Report quota risk only when predicted exhaustion precedes reset. Classify
  critical when it is within the greater of 60 minutes or 25 percent of the
  remaining window; otherwise classify the pre-reset risk as warning.
- [x] Implement monthly budget pacing from exact completed UTC days only:
  minimum five distinct days, at least 70 percent elapsed-day coverage,
  median compatible daily spend, no zero-filled missing days, and current UTC
  day excluded from both baseline and month-to-date spend.
- [x] Keep actual and estimated pacing separate and reject mixed value classes,
  mixed currencies, and budget-currency mismatches without conversion.
- [x] Derive `usable` and `strong` evidence mechanically from fixed sample,
  coverage, freshness, and median-absolute-deviation rules exposed by
  `methodContract`.
- [x] Add `GuardrailModel` as the asynchronous, superseding QML list model.
  Late generations cannot update rows; cancellation tokens, workers, watchers,
  and read-only database connections are released after completion.
- [x] Keep forecast results ephemeral. Only the Phase 1 transition API can
  persist warning, critical, or recovered events.

### Phase 5 — Notifications and integrations

- [x] Gate deterministic guardrail notifications behind both the existing
  global alert switch and the new opt-in forecast notification switch, which
  remains disabled by default.
- [x] Reuse provider enabled/notification controls and accept only configured
  lead times of 1, 6, 24, or 48 hours. A future warning/critical transition is
  not persisted until it enters the configured lead-time horizon.
- [x] Persist warning, critical, and recovered transitions before delivery.
  The schema-v5 transition API is the single delivery gate, so unchanged
  refreshes and the same state after database reopen produce no duplicate.

  unavailable. The unavailable message states that risk is no longer asserted,

  handling allow-lists provider source, risk kind, state, transition, timing,

- [x] Export current risk state and seconds to the earliest predicted event as
  Prometheus gauges aggregated by provider, risk kind, and value class only.
  No model, project, workspace, scope, stable-ID, or API-key labels are
  exported.
- [x] Keep integrations informational: no model switch, provider write, budget

Changed assumption and evidence:

- DND and the existing notification cooldown are evaluated before transition
  persistence. A suppressed transition therefore remains eligible on a later
  refresh after the suppression window, while a delivered transition is
  restart-safe.
- Forecast notifications require the local schema-v5 database even when
  general History is disabled. Enabling forecast notifications therefore
  enables the local database for the observations needed by the forecast and
  the minimum transition evidence; it does not enable external storage.
- Multiple compatible windows are collapsed to the worst current state and
  earliest predicted event for each provider/risk/value-class Prometheus
  series. This avoids a potentially unbounded window label and duplicate
  series while preserving actionable aggregate risk.
- Forecast Contract v1 names the budget risk `budget_overrun`; “budget pacing”
  is presentation terminology only. Notification and Prometheus branches use
  the contract identifier, and focused tests reject the non-contract
  `budget_pacing` identifier in integration code.
